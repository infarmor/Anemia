# Anemia для Android

Папка — **порт, который собирается, подписывается и работает**; экранов уже
больше одного, но до паритета с iOS по UI ещё есть куда идти. Что уже реально:

- **`:core` компилируется и проверяется.** `bash Android/Scripts/test-core.sh`
  собирает Kotlin-порт ядра (`core/src/main/kotlin`) и прогоняет его сверки с
  Swift — сейчас 43 проверки, все зелёные, и каждая трижды: под обычной локалью
  JVM, под `ar-EG` (десятичные цифры печатаются не ASCII) и под `tr-TR`
  (расширение `i` в верхнем регистре).
- **APK собирается и поднимает туннель.** `cd Android && ./gradlew
  :app:assembleDebug` (JDK 21, Gradle 8.10.2, platform 36, NDK r28 — всё
  поставлено, см. `Scripts/bootstrap.sh`) даёт `app-debug.apk` на три ABI, а
  на эмуляторе Android 16 он подключается к настоящему xray-серверу: `tun0` с
  адресами из плана, маршруты по умолчанию в таблице `tun0`, трафик приложений
  проходит сквозь движок и счётчики в уведомлении растут. Подробно — в
  «Проверка на эмуляторе» ниже.
- **Интерфейс — не один экран.** `ui/MainActivity.kt` (список серверов, вставка
  ссылки/строк/wg-конфига/тела подписки, подписки с заголовками, «Замерить» и
  «Лучший», обход, adblock, профиль маскирования, статус), статистика трафика и
  замер скорости, карта, экран утечек, перенос с QR, обход по приложениям,
  плитка Quick Settings. Не сделано: отдельный экран настроек и аналог
  `DiagnosticsView`; камерой QR не читается.
- **Тестов хоста у `:app` пять файлов, 47 тестов** (`app/src/test`): лестница,
  QR, учёт показаний AmneziaWG, ряд истории замеров и честность строк экрана утечек. Остальное держится
  золотом `:core` и прогонами на эмуляторе — см. разделы ниже.

Задача порта — не «переписать SwiftUI на Compose», а перенести два слоя, в
которых и живёт вся логика:

1. **движок** (Xray-core + AmneziaWG одним Go-архивом) — почти без правок;
2. **построение конфигов и разбор ссылок** (`Sources/LoaderCore`) — порт
   Kotlin-ом, с теми же тестами как мерилом.

Всё остальное — интерфейс и системные мостики — пишется заново под Android.

## Что на Android устроено иначе (и это к лучшему)

- **Туннель.** Вместо `NEPacketTunnelProvider`-расширения — `VpnService`
  (отдельный процесс, `BIND_VPN_SERVICE`). Дескриптор даёт
  `Builder.establish()`, и движок **сам** дублирует его (`dupNonblocking` в
  `engine.go`) — как на iOS, где тот же дескриптор принадлежит расширению.
  Никакого `AnemiaFindTunnelFD` не нужно: имена интерфейсов здесь не ищут, а
  вот закрывать за xray его копию приходится (см. «Проверка на эмуляторе»).
- **Живая скорость и «островок».** На iOS за это воевали: Live Activity
  обновляет только само приложение, поэтому — беззвучное аудио,
  `BackgroundKeeper`, фид раз в 4 с, `staleDate`, и вся охота за
  «пустым Dynamic Island». На Android счётчики снимает **тот же процесс,
  который держит туннель** (foreground service), и пишет их в
  `Notification`/`Tile` напрямую. Прослойка «приложение → активность»
  исчезает вместе со своими багами.
- **Раздельный туннель.** Домены по-прежнему резолвятся в IP (список
  исключённых маршрутов), зато появляется то, чего на iOS нет:
  `Builder.addAllowedApplication()` — обход VPN по приложениям.
- **Песочница одна.** App Group и `SharedStore` с угадыванием группы из
  профиля не нужны: виджет, сервис и интерфейс видят одни и те же файлы.
- **Память.** iOS убивает расширение на ~50 МБ, поэтому в движке
  `AnemiaSetMemoryLimit` и жёсткие буферы. Android лимита не ставит, но
  OEM-убийцы процессов (Miui, Samsung) убивают foreground service — нужен
  `START_REDELIVER_INTENT` и внятная переподписка на `NEVPNStatus`-аналог
  (свой статус-канал); про `setPowerMode` из iOS-списка — см. риск №3: этого
  API приложению не выдают.

## Риски, которые ещё не закрыты

1. **AmneziaWG на Android проверена живым сервером — и оказалась сломана
   (закрыто 2026-09-27).** Официальное приложение ходит в `libwg` через свой
   JNI; у нас движок единый, и `CreateTUNFromFile` на android попадает в
   linux-ветку `amneziawg-go`: ей нужны `TUNGETIFF` (флаги, `IFF_VNET_HDR`),
   `getIFIndex` и netlink-сокет для следования за интерфейсом. Дескриптор от
   `establish()` — `/dev/tun`, созданный netd с `IFF_TUN|IFF_NO_PI`, и на переходе
   к `CreateUnmonitoredTUNFromFD` ни netlink, ни `TUNGETIFF` не понадобились.
   Измерено с настоящим пиром (`Scripts/awg-peer.sh` поднимает `amneziawg-go` на
   реальном UDP-порту): `PEER VERIFIED: handshake settled, 301 bytes received
   from the client`, на устройстве `tun0` с адресом `10.66.0.2/32` ровно из
   конфига, в уведомлении `awg · 7,9 КБ · 42 с` — счётчики идут. Пир затем
   убит, и это второе доказательство: с открытым экраном `health: … (подряд 1)`,
   `(подряд 2)`, затем `connect C steady good` — мёртвый AWG-выход наконец
   замечен и оставлен (до правки порог здоровья на AWG не мог набраться).
   До этого прогона ветка не работала вовсе: движок отвергал наш же UAPI-скрипт
   — `awg config: IPC error -22: invalid UAPI device key: set`, — потому что
   `device.IpcSet` принимает тело операции, а рамочная строка `set=1` принадлежит
   сокетному протоколу `IpcHandle`. Чинится в общем движке (`iOS/Engine/engine.go`:
   срезка рамки + четыре Go-теста на неё), и из того же следует, что `.ipa` до
   пересборки движка не умел `awg://` тоже.
2. **`kxc`-ранжировщик.** CoreML-модель (`Resources/kxc.mlmodelc`) на
   Android не грузится: либо конвертация в TFLite/ONNX, либо откат на
   эвристику `ServerScoring` — порт `KxcFeatures` тогда всё равно нужен
   (он есть).
3. **Сон процесса туннеля — закрыто измерением, а не обещанием (2026-09-27).**
   Пункт был перенесён с iOS и оказался невыполнимым: ни `setPowerMode`, ни
   `POWER_MODE_PERFORMANT` нет ни в одном классе `android.jar` для API 36 (это
   скрытый API системных сервисов, приложению не доступен). Вместо него то же
   самое делает система: на каждом `establish()` netd регистрирует интерфейс
   источником пробуждения — `wakeupAddInterface(tun0, …)` в логе при подъёме и
   `wakeupDelInterface` при снятии, — то есть входящий пакет будит процессор сам.
   AOSP-овый doze процесс не морозит: `bash Android/Scripts/verify-doze.sh 40`
   при `deviceidle force-idle` с погашенным экраном оставил `tun0` поднятым, а
   часы наблюдателя в уведомлении продолжали идти — 36 с → 78 с за 40 с простоя
   (т. е. тикали всё время сна; встать они могли бы только с замороженным
   процессом). Лестница во сне поэтому работает. Неизмеримое остаётся одно:
   OEM-убийцы (Miui, Samsung), против которых у нас `START_REDELIVER_INTENT`
   и foreground-сервис типа `specialUse` с подтипом `vpn`.
4. **minSdk 28** выбран под `addDisallowedApplication`, но на 29 и 36 сборка
   проверялась только на 36 (эмулятор). Прошивки 28–29 остаются непроверенными.
5. **Подпись.** Debug-ключ Gradle; для раздачи нужен свой.

Политика Google Play из этого списка убрана осознанно: публикуемся только
APK'ом в обход магазина.

## Вехи

- **0. Инструменты.** ✅ `Scripts/bootstrap.sh` + cmdline-tools, JDK 21,
  NDK r28, platform 36, Gradle 8.10.2 через обёртку, `local.properties`.
- **1. Движок.** ✅ `Scripts/build-engine.sh` → `libanemia.so` и
  `libanemia_jni.so` на `arm64-v8a`, `armeabi-v7a`, `x86_64`; JNI-шим в
  `engine/jni/anemia_jni.c` (Go отдаёт чистые C-символы, JVM их сама не
  находит), экспорты сверяются `llvm-nm`.
- **2. TUN.** ✅ `AnemiaVpnService`: `prepare()` → `establish()` → fd движку;
  `START_STICKY`, отложенное переподключение, статус раз в 3 с, own-UID через
  `addDisallowedApplication` (вместо `protect()`: у движка свои сокеты в том же
  UID). Проверено на эмуляторе — см. ниже.
- **3. Конфиги.** ✅ Порт `LoaderCore` + golden-тесты против текущего
  macOS/iOS-JSON.
- **4. UI.** 🟡 Экран подключения + статистика трафика, карта, экран утечек и
  замер скорости; свои активности у переноса и обхода по приложениям.
  Настроек как отдельного экрана и диагностики в духе `DiagnosticsView` — всё
  ещё нет.
- **5. Обвязка.** ✅ Уведомление-статус, Quick Settings tile, App Shortcuts,
  QR и ссылка переноса, импорт `.anemia`, обход по приложениям. Домашним экраном
  tile и двум новым активностям пока не служатся — у них свои входы (шторка,
  ярлык, файл, `anemia://`); камерой QR не читается. Первый запуск на
  Android 13+ спрашивает разрешения по цепочке: согласие на VPN, затем на
  уведомления (раньше после VPN-согласия шёл сразу `connect()`, и на чистой
  установке туннель поднимался с `isForeground=true`, но в шторке было пусто —
  замерено на релизном APK).
- **6. Сборка.** ✅ `Scripts/build-apk.sh`: release собирается заново
  (`--rerun-tasks`) и подписывается; артефакты ложатся в `Android/dist/`
  (игнорируется git'ом — каталог AGP следующая сборка чистит, и три подписанных
  APK по ABI исчезали из него ровно после универсальной сборки). Универсальная
  пересборка идёт первой именно поэтому: пока полная сборка стояла последней,
  сборки по ABI упаковывали прошлые `.class` — правка была в дереве, но не в
  архиве (поймано на хэшах: `5dd13713…` → `250127d1…` без единой правки между
  ними). Проверка «артефакт актуален» — пересобрать и сравнить хэш; `UP-TO-DATE`
  для этого не годится. Кроме
  универсального делаются `anemia-release-<abi>.apk`: dex в них побайтово тот
  же, отличается только каталог `lib/` (сверено CRC записей). Ключ берётся из
  окружения, иначе — штатный ключ раздачи из `~/Library/Application Support/Anemia`,
  иначе — отладочный, и про отладочный скрипт говорит вслух.
- **6a. Размер APK.** Движок — 93 % архива (33 245 872 Б из 35 895 859 Б), поэтому
  `build-apk.sh` по умолчанию сжимает нативные библиотеки
  (`ANEMIA_APK_COMPRESS_LIBS=0` — вернуть): arm64-сборка 13 879 859 Б вместо
  35 895 859 Б, универсальная 37 829 640 Б вместо 103 578 632 Б. Плата — свои
  32 МБ в `/data/app/…/lib/arm64` после установки (`extractNativeLibs=true`,
  `libanemia.so` лежит распакованным); библиотека грузится оттуда, туннель на
  этой сборке поднят на устройстве. Пробовали вырезать лишние регистрации
  xray-core из движка (`main/distro/all` → только то, что издаёт билдер конфига,
  без CLI и без gRPC-управления): пересборка arm64 дала 33 046 000 Б — 0,6 %, и
  ценой этих 0,6 % был бы риск потерять протокол, который всё-таки собирается.
- **6b. Что мерили и не трогали.** `:vpn` на поднятом туннеле в простое стоит
  12 джиков за 60 с — 0,2 % ядра при тике в 3 с, так что реже тикать при
  погасшем экране незачем (а интервал тика — часть инварианта лестницы: «два
  тика = 6 с»). Холодный старт экрана 298–306 мс. Потолок кучи Go на Android
  (64 МБ против ≤40 МБ в расширении iOS) оставлен: замера под нагрузкой нет.
  `lintDebug` — 0 ошибок. Про `--rerun-tasks` не для аккуратности: обычный
  `assembleDebug` трижды ответил `UP-TO-DATE` по APK, пережившему вечернюю
  правку `:core`, и в хвосте того архива лежали байты, не принадлежащие ни
  одной записи.

## Проверка на эмуляторе

Сценарий целиком описан в `Scripts/verify-tunnel.sh` (его же можно повторить
на своём устройстве через `adb`). Ключевое — он сверяет наблюдаемые следы, а не
коды возврата:

```
tun0 172.19.0.1/30 fdfe:dcba:9876::1/126     ← адреса из плана
default dev tun0 table tun0                   ← и v4, и v6
from all fwmark … uidrange 0-10212 lookup tun0
from all fwmark … uidrange 10214-99999 …      ← UID приложения вырезан
access.log сервера: accepted tcp:mtalk.google.com:5228 [test-in >> direct]
```

Последняя строка — настоящее приложение телефона, донесённое туннелем до
xray-сервера на Mac (`10.0.2.2`): `./Resources/xray run -c
Android/Scripts/tunnel-server.json` поднимает этот сервер, а лог доступа
пишет в текущий каталог (`tunnel-access.log`, в `.gitignore`) — там видно,
что именно прошло через туннель. Трафик `adb shell` в туннель не попадает:
Android выводит root/shell UID из VPN сами по себе, и это стоит помнить,
когда «ping не работает» выглядит как баг туннеля.

Три вещи, которые нашлись только таким прогоном:

* **`stopService()` туннель не рвёт.** Пока интерфейс жив, сетевой стек держит
  свою привязку к сервису, и система не даёт ему умереть: `startRequested`
  сбрасывается, а сервис, уведомление и `tun0` живут. Отключение — команда
  самому сервису (`EXTRA_DISCONNECT`), который закрывает дескриптор и гасит
  себя.
* **xray не закрывает выданный ему дескриптор.** `AndroidTun.Close()` в
  xray-core — пустая функция (на iOS то же делает ветка `ownsFd == false`
  у `DarwinTun`), поэтому после `instance.Close()` в процессе остаётся дубль
  `/dev/tun`, и ядро держит интерфейс. Проявилось как «отключили — а tun0
  висит»: теперь `stopLocked` в `engine.go` закрывает свою копию сам (это же
  чинит и молчаливую течь на iOS, где процесс расширения умирал и прятал её).
* **второй `establish()` поверх живого туннеля даёт интерфейс без маршрутов.**
  Снятие предыдущего асинхронное: без ожидания новый `tun` поднимался DOWN,
  с нулём маршрутов и замороженными счётчиками — то есть мёртвый туннель
  выглядел живым. Теперь перед подъёмом сервис ждёт, пока интерфейс исчезнет
  (до 4 с), а после — что он появился (до 2 с), и пишет в статус, если нет.

## Второй проход: три независимых сканера на слой приложения

Сканеры делили работу так: жизненный цикл и нити в `:app`, сверка
`ConfigApplier` с `TunnelPlan.swift`, и harness вокруг нового `Persistence.kt`.
Что подтвердилось и исправлено (каждое — либо замером, либо найденным в
исходниках движка путём):

* **AmneziaWG на Android не поднималась вовсе.** `GOOS=android` берёт
  linux-ветку `amneziawg-go`, а `CreateTUNFromFile` в ней безусловно вызывает
  `setMTU` (`SIOCSIFMTU`) и поднимает netlink-слушателя. MTU интерфейса принадлежит
  `VpnService`, а менять его можно только с `CAP_NET_ADMIN`, которого у
  приложения нет: `awg://` кончалось ошибкой движка. Перешли на
  `CreateUnmonitoredTUNFromFD` — тот только оборачивает готовый дескриптор и
  закрывает его на `Close()` (на iOS путь остался прежний, `tun_darwin.go`
  ничего не настраивает). Заодно дескриптор теперь закрывается и при неудачной
  сборке устройства, а не утекает.
* **Профиль маскирования не доезжал до конфига.** iOS берёт `setup.masking.options`,
  Android молча ставил `recommended`: ни `Max`, ни `RU·Ya` на телефоне не
  существовали. Теперь туннель получает `TunnelSetup` — ту же модель, что iOS
  кладёт в `providerConfiguration` (и не текст ссылки: у сервера из подписки
  ссылки нет, а повторный разбор менял бы ему `id`, на котором держатся
  выученное маскирование и история проб).
* **`bufferSizeKB` и лимит памяти Go.** iOS просит 4 КБ буфер и ставит
  `SetMemoryLimit`; Android не просил ни того ни другого (512 КБ на соединение и
  без лимита). Буфер теперь тот же, лимит — 64 МБ, и он обоснован в коде другим
  основанием, чем на iOS.
* **`START_STICKY` не работал как задумано.** Переподключение после
  OEM-убийцы требовало `START_REDELIVER_INTENT`: sticky доставляет `null`, а без
  setup'а подключаться нечем.
* **Подъём туннеля стоял на главной нити процесса** — до ~12 с на худом DNS и
  двух ожиданиях интерфейса. Теперь всё на отдельном `HandlerThread`;
  `startForeground` по-прежнему делается сразу в `onStartCommand`.
* **Отказ подъёма оставлял foreground-уведомление висеть вечно** («подключение…»
  мигрировало в «Конфиг не собрался» и не снималось). Теперь ошибка уходит в
  неснимаемое-но-смахиваемое уведомление, а сервис гасит себя.
* **`onRevoke` не переопределялся**: реализация по умолчанию — `stopSelf()`, а он
  туннель не рвёт (см. выше). Теперь отзыв закрывает дескриптор.
* **Релизная сборка теряла движок.** `isMinifyEnabled = true` без keep-правил:
  R8 переименовывает `app.anemia.vpn.Engine`, а JNI ищет `Java_app_anemia_vpn_
  Engine_*` по имени → `UnsatisfiedLinkError` и «Движок не загружен». Добавлены
  `proguard-rules.pro` и `proguardFiles`.
* **`state.json` уезжал в резервную копию** вместе с приватными ключами —
  `allowBackup="false"`. И сам файл теперь пишется с правами 0600 (замерено на
  устройстве: `-rw------- u0_a213`), как это делает `.atomic` на iOS.
* **`POST_NOTIFICATIONS` не запрашивался** — на 13+ уведомление о туннеле просто
  не показывалось. Теперь перед первым подключением спрашивается (проверено:
  диалог «Allow Anemia to send you notifications?» → Allow → туннель поднят).
* **Экран не учитывал edge-to-edge** (targetSdk 36): заголовок залезал под
  статус-бар. Добавлен `safeDrawingPadding`.
* **Шим возвращал «загружено» при неполном наборе символов**: `if (lib != NULL)
  return 1` проверял ручку `dlopen`, а не указатели — старая `libanemia.so` без
  половины экспортов приводила к прыжку в NULL. Появился флаг `resolved`.
* **Запись состояния не была атомарной на самом деле**: временное имя
  `<файл>.tmp-<мс>` совпадало у двух писателей в одну миллисекунду (замерено:
  92 пустых и 8 обрезанных чтений на пару из 800 записей), а неудачное
  переименование писало поверх боевого файла. Теперь уникальное имя из
  `createTempFile`, `ATOMIC_MOVE` с ошибкой вместо записи на месте, выметание
  осколков при чтении и права 0600.
* **Валидация конфига и адреса AWG расходились с iOS**: порядок проверок (сначала
  замечания валидатора, потом профиль) и текст «нет профиля» — теперь как в
  `TunnelPlan`; адреса интерфейса берутся все, со своими префиксами, а не первый
  IPv4 как `/32` (проверка «адреса туннельного интерфейса из профиля»).
* **Список обхода игнорировал свой главный выключатель**: брался `entries`, а не
  `activeEntries`, — то есть при выключенном списке Android всё равно выводил бы
  эти сети из туннеля.

Отдельно и дороже всего: `Persistence.kt` был **мёртвым кодом** — сборка без
него давала те же зелёные 32 проверки. Теперь у файлового слоя есть своя
проверка на настоящем каталоге, и восемь внесённых в него мутаций (обратная
сортировка prune, «оставлять пять», страховка не пишется, нечитаемый файл =
порча, осколки не выметаются, `10.8.0.5/` как `/32`, порядок семейств, IPv6 без
префикса) краснеют все. Число проверок закреплено в `test-core.sh`: удалить
`check(...)` из `main()` больше нельзя незаметно (проверено — `rc=1`).

Чего скан не нашёл адресно, но стоит помнить: `InetAddress.getAllByName` не
прерывается по `interrupt()`, поэтому на чёрной дыре в DNS висит до 40 потоков
по ~полминуты (тот же след и на iOS); Modified UTF-8 в JNI не переносит
дополнительную плоскость Unicode — ссылка с эмодзи в `path`/`xhttpExtra`
расберётся, но в конфиге станет мусором; и `dlopen("libanemia.so")` опирается на
то, что обе библиотеки лежат в одном namespace загрузчика (на эмуляторе
проверено, но это предположение, а не гарантия).

Проверки сравнивают вывод Kotlin байт-в-байт, так что переименованный или
переставленный ключ и изменённая логика видны сразу. Вторым контуром идёт сам
движок: `verify-configs.sh` прогоняет каждый эталонный конфиг через `xray -test`,
и он уже ловил то, что сверка двух парсеров не показала бы — например что
1184-байтный «ключ» ML-KEM проходит грамматику, но движок падает на нём при
инициализации, а `encryption` из ссылок старого формата движок не принимает
вовсе (теперь это отказ с внятным текстом, а не мёртвый туннель). Имена стран сверяются
отдельно и проверку не роняют: `US` в CLDR Apple — «Соединенные Штаты
Америки», в CLDR JVM — «Соединенные Штаты». Это разные версии одной базы, и
порт обязан сообщить о расхождении, а не молча выбрать одно. Та же судьба у
таблицы алиасов: `RUS` и `UK` Apple разворачивает в названия, десктопная JVM —
нет; на Android'е за имена отвечает ICU, и что именно она ответит, этот прогон
не измеряет — поэтому `codes.tsv` роняет проверку только там, где расходимость
в *решении* («нашли название» против «вернули код»), а разницу словарей печатает
списком.

Три вещи из этого прогона стоят того, чтобы помнить о них при следующем порте:

* **десятичные цифры зависят от локали JVM, а в Foundation — нет.**
  `"%02d".format(9)` под `ar-EG` даёт `٠٩`, тогда как `String(format: "%02d", 9)`
  и `\(9)` в Swift печатают ASCII при любой языковой настройке устройства. Так
  расходились ключ дней трафика (`2026-09-24` против `٢٠٢٦-٠٩-٢٤` — и
  `date(ofDay:)` потом не читает собственный ключ), `1:12` в углу острова и
  имена признаков `f00`…`f24`, которыми модель ищет входы. Все три места теперь
  пишут через `Locale.ROOT`, а проверить это можно только вторым прогоном под
  арабской локалью: эталон-то из Swift, и он от локали не зависит.
* **`Char.isWhitespace` — не тот набор, что `.whitespacesAndNewlines`, и держится
  он не одинаково на разных JVM.** На встроенной в Android Studio (JBR 25) NBSP
  считается пробелом, на Android'овом libcore — нет, поэтому `trim()` совпал бы
  с Foundation здесь и разъехался там. Набор задан руками (`isSpaceLike`,
  `isFoundationSpace`) и сверяется таблицей `base64/trim-sets.tsv` — посимвольным
  членством, а не разбором значений: золотой файл такую мутацию не видит. Заодно
  таблица поймала, что `isFoundationSpace` считал пробелом перевод строки,
  которого в `.whitespaces` нет.
* **`Double(String)` в Foundation — это `strtod`, а не JSON-число.** Он не
  терпит пробелов вокруг, принимает `0x1f`, `inf`, `NAN`, `nan(1)` и ведущий `+`,
  и отвергает `١٢٣`. `String.toDoubleOrNull`/`toLongOrNull` делает наоборот:
  пробелы проглатывает, hex-дроби не знает, спецслова читает только в написании
  `NaN`/`Infinity`, а арабские цифры переваривает. Для заголовков панели это
  значит квота есть на Android и нет на iOS. Порт разбирает сам
  (`core/…/FoundationNumbers.kt`, `SwiftDouble` и `SwiftInt`), и 102 случая грамматики
  лежат в `sub/numbers.txt`
  hex'ом — иначе кейс с вертикальным табом или переносом не влез бы в строку
  фикстуры, — а ответ сравнивается битом IEEE-754, чтобы `-0` не пряталось за
  `0`. Та же грамматика отдельно закреплена для `UInt32` в валидаторе AWG:
  `H4 = 1-+9` Swift принимает, `H2 = ١٢٣` и `H1 = -5-999` отвергает, а `H3 = 0x1f`
  — принимает, и именно этот кейс поймал регрессию, которую я сам внёс первым
  вариантом фикса (он отвергал hex с буквами).

Второй проход скана (три независимых сканера: Kotlin-порт, Swift-сторона
harness'а и сам механизм сверки) добавил ещё класс расхождений — те, что
 видны только на реальных длинах и вставках:

* `SplitTunnelParser` и разбор wg-quick конфига резали текст по
  `lineSequence()` — только CR/LF, а Swift по `\.isNewline`, где разрывом
  строки считаются ещё VT, FF, NEL, LS и PS. Вставка правил обхода,
  скопированная из страницы или PDF, на Android становилась одним мусорным
  правилом вместо двух — то есть трафик, который должен идти мимо туннеля,
  в туннель попадал.
* `DecimalFormat` в форматах скорости/байтов был с `isGroupingUsed = false`,
  а `.number` в Foundation группирует разряды неразрывным пробелом:
  «1 000 ТБ» против «1000 ТБ». На лестнице до этого доходит — верхняя
  ступень не ограничена thousand-м.
* Код страны в начале имени брался как два `Char`'а UTF-16, а Swift берёт
  два графемных кластера: «DE◌́-01» (E с объединяющим ударением) читался
  как `DE`.
* `expire=0` во втором вхождении заголовка: Swift присваивает без условия и
  тем самым *сбрасывает* срок, порт же оставлял прежнее значение.
* `Json.int()` и разбор портов/префиксов опирались на `toIntOrNull()`,
  который на JVM проглатывает не-ASCII цифры в середине («1٠» → 10).
* Валидатор профиля принимал только 44-символьный base64 ключ, тогда как
  билдер (`hexKey`) строит конфиг и из 64 hex-символов — то есть ругался на
  конфиг, который потом сам же и поднимает.

Изменён и сам механизм. `verify-state.sh` и `verify-sync.sh` больше не могут
пройти на нуле: пропавший файл, который должен был перечитать Swift, — это
красный результат, а не `continue` (проверено прогона на пустом каталоге:
`rc=1`). Проверки конфига движка и AWG сверяют теперь *полноту*: лишний
`.json`/`.err`/`.uapi` без кейса в фикстуре падает так же, как пропущенный
кейс, а таблица пробелов обязана покрыть различающие кодовые точки. Дамп
полей сервера в золоте подписки — тот же, что в золоте ссылок (34 поля
вместо 17), иначе половина модели в подписке не сверялась вовсе. И допуск
«сходится в один бит» в сверке рейтинга снят: после отказа от `pow` обе
стороны обязаны совпадать побитно, иначе допуск глотает настоящие мутации
(сдвиг `rankingScore` на один ULP краснит 32 числа).


Пока это единственный в репозитории механизм, связывающий три платформы одним
поведением, — и он уже нашёл настоящие баги в iOS-слое:
`Dictionary(uniqueKeysWithValues:)` с `fatalError` на ссылке вида `?Obfs=x&obfs=y`
(краш при импорте подписки), percent-encode'ый base64-логин в `ss://`, где
`%3D` расшифровывался как часть алфавита и давал неверный пароль, мёртвая
ветка двойного base64 в `wireguard://`-userinfo (`decoded.count == 32` при
требовании 44 символов) и зависящий от порядка обхода словаря выбор
`obfs-password` в hy2. Подписочный слой добавил ещё три: `total` за пределами
`Int64` ловил trap в `Int(Double)` (краш посреди обновления), `used = upload +
download` переполнялся на тех же размерах, а тело подписки с CRLF не расклеивалось
по строкам вообще — `"\r\n"` в Swift один графемный кластер, и сравнение с `"\n"`
или `"\r"` не совпадает никогда; вся подписка после первой ссылки уезжала в
название первой. Нашёл именно перенос: Kotlin обязан сойтись с Swift
поле в поле, а не пройти ревью. Тот же контур ловил и ошибки самого порта —
`2026-2-02` вместо `2026-02-02` в дате бандла, молчание вместо отказа на
`specialHandshakes` с мусором внутри, пустой массив без пустой строки внутри.

Границу, которую буквально перенести нельзя, тоже записали: Swift печатает
дроби по-своему (там, где JVM даёт `4.9E-324`, Foundation — `5e-322`), поэтому
`state.json` сверяется разбором, а не байтами. Байтами сверяется бандл — дробей
в нём нет вообще, даты пишутся в ISO8601.

Золотые сверки проверяют и себя: каждый контракт зафиксирован мутацией — 39
попыток сдвинуть Kotlin, и каждая должна покраснеть (выжили 8, все восемь
стали кейсами: пустое `loc=`, скаляр вместо коллекции, tie-break prune, месяц 13,
адрес IPv6 без скобок, hopping мимо порта, пустой адрес hysteria, сетевой ключ
маскирования и верхний байт длины кадра) — в Kotlin вносился маленький сдвиг (принять пустое
значение `loc=`, простить запись bash.ws без `type`, снять потолок шага, принять
`2026-13-01`, сократить дробь в дате до трёх цифр, принять UUID вида
`0-0-0-0-0`), после чего прогон должен покраснеть. Так нашлись четыре кейса,
которые эталон не проверял, и одна настоящая ошибка порта: Foundation принимает
дробь любой длины (`.25Z`, `.250000Z`), а мы требовали ровно три цифры.

Прогон после скана — ещё 34 мутации (первый проход) и 12 (второй), и первые четыре выживших оказались не
эквивалентными мутантами, а дырами в фикстурах: `H1 = -5-999` вообще не доходил
до проверки знака (`parseRange` режет по первому дефису, и `value()` видит
пустую строку), пин с вертикальным табом не попадал ни в один кейс конфига, а
`trim()` на этой JVM сам снимал NBSP, поэтому кейсы на NBSP ничего не проверяли.
После добавленных `H2 = ١٢٣`, `H3 = 0x1f`, `H4 = 1-+9`, `hy2-pin-vtab`/
`hy2-pin-nbsp`, `userinfo-vtab` и таблицы членства убиты все, кроме двух:
`u%04x` и `%02x` без `Locale.ROOT` покраснеть не могут — шестнадцатеричные
цифры JVM не локализует (замерено), так что эти два `Locale.ROOT` —
подстраховка на будущее, а не закреплённый фикс.

Второй проход добавляет к этой статистике 12 мутаций — и все двенадцать
краснеют: `+443` в hopping, `lineSequence()` в обоих разборчиках строк,
выключенная группировка разрядов, два `Char` вместо графем, `expire=0`,
`toIntOrNull` в `Json.int()`, «ключ только base64», `nan(<мусор>)`, не-ASCII
цифры в `SwiftInt`, фолбэк названия по `isEmpty` и сдвиг `rankingScore` на
один ULP. Единственное, что закрепить не удалось, — возврат `pow(x, 2)` в
`ServerScoring`: на корпусе из 36 историй он не расходится с `x·x` ни на бите
(значения, где libm и JVM расходятся, существуют — 527 из 400 000 в
переборе, — но в этот корпус не попали). Умножение оставлено как есть: оно
убирает класс риска целиком, но честно сказать надо — эталоном это не
проверяется.


Скоринг пришлось приводить к этому же: `pow(decay, k)` и `pow(x, 1.5)` в
`ServerScoring.stability` две математические библиотеки считали с расхождением до
2 ULP, и золотой сверки это не проходило. Теперь веса домножаются
последовательным умножением, а `x^1.5` — как `x·√x`: только операции, которые
IEEE обязывается округлять одинаково. На порядок серверов это не меняет (сдвиг
1e-16 не перевешивает ни одного разделения в дереве), но заметим: свёрнутая
модель ранкера обучена ещё по старым битам, при ближайшем переобучении
`Scripts/kxc` возьмёт новые.

Не перенесено: сам обмер задержки (`NWConnection` → на Android это `SSLSocket`,
и тайминги двух стеков сравнивать нечестно), сокеты `PortFinder`, `getaddrinfo`
в `DirectResolver`, `SpeedTester`, сокетная часть `XrayStatsAPI`, `EngineLog`,
`PhysicalInterface` и `AsyncRace` — из них перенесены правила, а не вызовы.
Из `app/` перенесено ровно столько, сколько нужно для одного подключения, —
см. таблицу «Что в `app/`».

## Третий проход: скан слоя приложения и харнесса

Четыре сканера: жизненный цикл `:app`, сверка с `TunnelPlan`, файловый слой и
харнесс, и отдельный — безопасность. Подтвердилось и исправлено:

* **Уборка временных файлов в `load()` была гонкой, а не гигиеной.** Читающий не
  знает, чья запись не завершилась; интерфейс пишет состояние в тот момент, когда
  `:vpn` перечитывает файл перед подключением, — и «уборка» съедала чужой
  незаписанный файл, а `save()` падал и правка терялась (мерка: 171
  `NoSuchFileException` на 600 пар save/load). Убрана.
* **Документ в UTF-16 считался испорченным.** `JSONDecoder` Foundation читает
  UTF-8/16/32 по BOM; `String(raw, UTF_8)` из такого текста делает мусор, а за
  мусором следует страховка и пустой список серверов вместо ровно того же
  состояния. Теперь кодировка угадывается по BOM, BOM снимается.
* **Страховка писалась неатомарно**, хотя комментарий обещал обратное (у Swift
  `.atomic` с откатом — у нас обычный `writeBytes` и «откат», повторяющий тот же
  вызов).
* **Имя файла страховки для файлов без расширения** (`deletingPathExtension` у
  dotfiles ничего не снимает) расходилось с Swift; каталог-притворщик с именем
  страховки больше не занимает слот в prune.
* **`redirect` искался по регистру.** `HttpURLConnection` сохраняет написание
  проводов, а http/2 приносит `location` строчными — каждая переадресация от
  такой панели гибла как «redirect without a target». Плюс запретил падение
  https → http (это не перенаправление, а снятие защиты) и общий бюджет на всю
  выдачу: `readTimeout` меряет одно чтение, и медленная капля держала
  загрузку открытой вечно, блокируя кнопки.
* **Тело не-UTF-8 импортировалось с кракозябрами** вместо отказа: Swift на
  битой кодировке даёт nil и пустую строку.
* **Подписка вставлялась до загрузки** — опечатка в URL оставляла вечную
  «0 серверов», а каждая повторная попытка добавляла следующую. Теперь, как в
  Swift: сначала загрузка, строка появляется только при успехе.
* **Правило «выбранный сервер исчез — перенести выбор»** было потеряно при
  порте: панель, переименовавшая ссылку, оставляла в состоянии id, которого нет
  (он ещё и уезжал на Mac/iPhone вместе с `state.json`).
* **`TunnelSetup` разбирался снисходительно**: поле неверного типа молча
  превращалось в «обхода нет» или «balanced». Swift роняет весь документ — и
  подключение отказывает громко. Теперь так же.
* **Магазин пересоздавался на каждый поворот экрана**, а фоновый поток загрузки
  держал старый экземпляр и писал файл исподтишка нового. Теперь один на процесс.
* **Состояние магазина правилось из двух потоков без замка** (интерфейс и нить
  загрузки), `info` панели читался из композиции во время записи. Замок + снимок.
* **`setBypass` резал только по переводам строки**, хотя поле обещает и запятые,
  и всегда ставил `enabled = true`; хранил сырые строки вместо формы Swift
  (нормализованные принятые плюс отвергнутые, чтобы ничего набранного не
  потерялось).
* **Отказ подключения не доходил до глаз**: `fail()` не слал широковещательное
  сообщение, а `onDestroy` снимал уведомление об ошибке вместе с сервисом. Плюс
  «интерфейс не появился» был предупреждением, а не отказом — то есть ровно тот
  живой с виду мёртвый туннель.
* **Тик статуса брал мьютекс движка на главной нити** процесса туннеля
  (`AnemiaStatus` блокируется на всём времени `xray.Close()`), а `onDestroy`/
  `onRevoke` закрывали дескриптор, когда рабочий поток был между `establish()` и
  стартом движка. И тик, и разбор — на рабочем потоке.
* **`START_REDELIVER_INTENT` возвращал к жизни удалённый сервер**: пересылка
  приносит старый setup, и он подключался, даже когда сервера в списке больше
  нет. Теперь сервис сверяет id с `state.json`.
* **Мусорный extra ронял процесс** `RemoteServiceException`: выход до
  `startForeground()` при старте как foreground-сервис. Теперь отказ
  сопровождается уведомлением.
* **JNI не проверял ни `NULL` от `GetStringUTFChars` (память кончилась — и Go
  получает NULL), ни висящее исключение после `NewStringUTF`** — последнее
  уезжало в следующий нативный вызов и падало не там, где случилось.
* **Манифест переобъявлял себя**: `QUERY_ALL_PACKAGES` и `<queries>` без единого
  места, где список пакетов читают; `glance`/`datastore`/`security-crypto` в
  зависимостях без кода — а glance дополнительно привозил WorkManager с
  `WAKE_LOCK`, `RECEIVE_BOOT_COMPLETED` и экспортированными сервисами. Всего в
  APK теперь шесть разрешений, ни одного лишнего сервиса.

Что закрепилось и в харнессе: число конфигов, уходящих в `xray -test`,
пинится (`verify-configs.sh` краснеет, если до движка доехала половина
каталога), число проверок пинится в `test-core.sh`, prune сверяется с эталоном
Swift, а `verify-tunnel.sh` больше не засчитывает туннель без маршрутов по
умолчанию и не выходит нулём при ✗.

Осознанные расхождения, которые остались и не чинятся: `state.json` пишется
компактно, а не `prettyPrinted`; права выставляются 0600, чего `.atomic` на iOS
не делает; уникальность имени временного файла держится структурой вызова, а не
тестом; `getAllByName` не прерывается по `interrupt()`; Modified UTF-8 в JNI не
переносит дополнительную плоскость Unicode.

## Подписки

Панель (3x-ui, Marzban, RealityEZPZ…) узнаётся по `User-Agent`, поэтому заголовок
`v2rayN/6.26` — не косметика: без него вместо списка ссылок приходит HTML-страница.
Ответ панели живёт в двух местах: тело разбирает `SubscriptionParser`, заголовки
(`subscription-userinfo`, `profile-title`, `profile-update-interval`) —
`SubscriptionInfo`, и экран показывает имя, остаток трафика и срок из них.

Правило, выстраданное на macOS: пустой или мусорный ответ — **отказ загрузки**, а не
«серверов больше нет». Сохранение пустого результата стирало список при каждом сбое
провайдера. Проверено на устройстве против `subscription-panel.py`: панель приняла наш
`User-Agent`; подписка с телом-мусором и подписка с `403` добавились строчками
«0 серверов», тогда как соседняя (рабочая) сохранила и два сервера, и выбор;
текст отказа на недоступный адрес экран показывал в той же форме, что и macOS
(`Fetch failed: HTTP 404`, `Fetch failed: Failed to connect to …`).

`http://` разрешён (`res/xml/network_security_config.xml`) — ровно как
`NSAllowsArbitraryLoads` в `LoaderApp-Info.plist` на macOS. Это осознанный выбор в
пользу совместимости с чужими панелями, а не защита: трафик туннеля шифруется так,
как описал сервер, а по http ходит только список серверов.

Но список без TLS отвечает так, как хочет тот, кто держит путь: роутер в кафе
вернёт свои серверы, а через подставные уйдёт уже шифрованный трафик. Поэтому
всё решение «можно ли панели поменять список без пользователя» собрано в одном
предикате — `Subscription.refreshIsDue(now:panelInterval:defaultAge:allowInsecure:)`
на Swift и `refreshIsDue`/`refreshMaxAge` на Kotlin. Он же золотой:
`Scripts/golden-sub.sh` гоняет 28 кейсов `sub/due.txt` через `LoaderTool subdue`
и сверяет байт в байт (`Checks.kt`, 36-я проверка). Пять мутаций предиката —
`>=` → `>`, нижняя граница зажатия, снятый TLS-гейт, игнор `allowInsecure`,
дефолт 21600 → 21601 — красят и Kotlin-проверку, и новый Swift-тест
`testSubscriptionAutoRefreshDecision`.

Панель без шифрования не готова никогда, поэтому автообновление пропускает её
молча, а строка подписи «без шифрования». Нажатие человека («Обновить все»,
кнопка `обновить` у строки) грузит и http: знак виден, решение за человеком.

Автообновление на Android теперь есть: `AnemiaApplication` поднимает круг через
10 с после старта процесса и повторяет проверку каждые 5 мин, дальше решение
за предикатом. Три вещи, которые дало только устройство:

- панель, у которой загрузка стабильно падает, не должна дёргаться каждые
  пять минут: `lastUpdated` у неё не двигается, и без отметки `lastAttempt`
  она крутилась бы вечно. Порог повторного запроса — тот же интервал панели;
  на macOS и iOS за то же отвечает редкий собственный круг (6 ч и полчаса);
- заголовки панели (`осталось 1,1 ГБ`, `до 2099-12-31`, имя,
  `profile-update-interval`) переживают перезапуск: на macOS и iOS они в
  UserDefaults, здесь — `shared_prefs/anemia-panels.xml`. В `state.json` они
  не едут: это общий со Swift формат, а Swift таких ключей не читает. Без
  кэша строка теряла остаток и срок после каждого запуска, пока панель ещё
  не созрела для нового запроса;
- процесс туннеля (`:vpn`) тоже создаёт `Application`, и без проверки имени
  процесса раундов было бы два — на один `state.json`.

Прогон на устройстве (2026-09-26, `subscription-panel.py` на 8080 и её же
https-обёртка на 8443): раунд `ready=1 loaded=0 skipped-no-tls=1` — мёртвая
https-панель тронута, живая http-панель не тронута вовсе (счётчик запросов
панели за время двух кругов не сдвинулся); отказ https —
`Fetch failed: java.security.cert.CertPathValidatorException: Trust anchor for
certification path not found`, то есть недоверенный сертификат не проходит;
кнопка «Обновить все» ту же http-панель грузит (строка становится «осталось
1,1 ГБ · до 2099-12-31 · обновлена 2026-09-26»), и после force-stop всё это
останутся на экране. Обратный ход проверялся отдельно собранной версией с
укороченным кругом в 30 с: первый раунд `ready=1`, следующий `ready=0` —
backoff работает.

Пять находок, которые дал скан нового кода и которые подтверждены чтением или
 прогоном:

- `ServerStore.remove()` писал состояние вне замка, а фоновый `refresh()` держал
  снимок 30 с и потом писал список целиком — удалённый сервер возвращался и в
  память, и в `state.json`. Теперь правка идёт через `mutate`.
- Причина отказа лежала в общем поле `lastFailure`: две параллельные загрузки
  показывали ошибку чужой панели. Результат теперь возвращается вместе с
  ошибкой (`Fetched.Ok`/`Fetched.Failed`).
- Круг не поднимал `busy`, и нажатое поверх него «обновить» запускало вторую
  загрузку того же URL: два `carryingIDs` из разных снимков. Добавлен
  `refreshing`, как на iOS; круг занятую панель просто не трогает.
- `JSONObject.put(String, double)` бросает на NaN и ∞, а вызов шёл из фонового
  потока загрузки: панель с `profile-update-interval: 1e400` роняла приложение.
  Нечисловые значения отсекаются на разборе заголовков (обе стороны), а
  писатель кэша их просто не кладёт; `optLong`/`optDouble` вместо выдуманных 0 и
  NaN читают только `Number`.
- Живой выход мог исчезнуть из списка молча — и туннель продолжал идти через
  отозванный сервер, а экран показывал «подключено». `:vpn` теперь раз в минуту
  сверяет сервер сессии со списком и рвёт соединение с причиной в уведомлении
  (то же правило на macOS ведёт к `disconnect()`). Проверено на устройстве:
  живой `tun0` через 10.0.2.2, сервер исчезает из `state.json` — через минуту
  `Device "tun0" does not exist`, в уведомлении и на экране «Сервер исчез из
  подписки — соединение разорвано».

Ещё: отметки `lastAttempt` и кэш заголовков чистятся по живым подпискам (раунд
не оставляет мусора от панелей, удалённых год назад); пустой список больше не
производит «круг» и строчку в логе каждые 5 мин; `reload()` отличает «кэш уже
прочитан» от «кэш пуст»; экран перерисовывается и когда круг оборвался на
середине; в Compose `busy` снимается после `notice`, а поле ссылки не затирает
то, что человек набрал за 30 с ожидания.

## Задержки, история проб и лучший сервер

Тот же инструмент, что на macOS: `LatencyProber` мерит время TLS-хэндшейка (или
одного TCP-коннекта, если TLS нет), `ProbeStore` ведёт ряды и рейтинг, экран
показывает задержку в строке и отмечает лучшего.

Правила замера — не «как получилось», а порт `LatencyProbe.swift`, и часть из
них вообще живёт в `:core` (`Probing.target`, `Probing.collect`, закреплённые
золотом): 5 попыток по 4 с, ранний отказ после двух промахов, пул из 6 серверов
(больше — SYN-шторм и самопомеха, из-за которой подписка ранжирует себя по
тому, как сильно она же и забила канал). SNI подаётся по правилу `target`: IP-
литерал имени не получает, потому что несколько серверов рвут хэндшейк с
литералом в SNI; Reality/CDN-фронт, наоборот, получает имя из ссылки, иначе
фронт отклоняет хэндшейк и рабочий сервер читается мёртвым.

Сертификат не проверяется намеренно: мы измеряем рукопожатие, а маскирующие и
самоподписанные сертификаты у таких серверов — норма; по этому соединению
ничего не передаётся. Отдельно от загрузки подписок, где недоверенный сертификат
как раз рвёт соединение.

Что остаётся открытым нарочно:
- модель kxc на Android не перенесена — «лучший» считается эвристикой
  `ServerScoring.rankingScore` (та же функция, что у Swift, и сверяется золотом),
  а не обученной моделью; quality-уровней, как на macOS, пока нет;
- экран не знает, какой сервер сейчас несёт туннель (канала статуса с id
  сессии нет), поэтому во время поднятого туннеля замеры показываются, но в
  историю не пишутся вовсе — macOS пишет их хотя бы для подключённого сервера,
  а двойной прыжок клиент → выход → сервер ряды портит;
- серверы WireGuard-семейства и hysteria проба мерит так же, как на macOS:
  коннектом по TCP, то есть «нет ответа». Это совпадение с эталоном, а не
  проверка транспорта.

Проверено на эмуляторе (2026-09-26) против локальных слушателей: xray на
10443 без TLS, TCP-эхо на 8388 и TLS-сервер на 10843 с самоподписанным
сертификатом. Ряды: 383 мс, 303 мс, «нет ответа» на `nope.invalid`, 789/790 мс
на двух TLS-серверах (хэндшейк дороже коннекта — ровно та методика, что у
macOS); `5 sni='probe.test'` и `5 sni=None` в логе сервера — это правило IP-
литерала видно на проводе, по пять попыток на каждый сервер. `history.json`
переживает перезапуск: после force-stop задержки в строках еще не мерили («—»),
но «лучший» и «Выбрать» работают по сохранённым рядам. Для порядка: коннект
через пользовательский NAT эмулятора стоит ~300 мс (замерено `nc` из шелла
устройства: 287/489/496 мс), поэтому абсолютные числа здесь — свойство рига, а
не сервера; значимы порядки и «жив/мёртв».

## Шестой проход: что нашёл скан в сервисе и в замерах

- `onDestroy` ставил разбор на рабочий поток и **тут же** звал
  `removeCallbacksAndMessages(null)` — то есть стирал только что поставленный
  `Engine.stop(); closeTunnel()`. Итог: убитый процесс оставлял движок жить с
  дубликом туннельного дескриптора, а уведомление «подключено» висело над
  мёртвым выходом (тот же блок в `onRevoke` мог быть выметан гонкой). Строка
  удалена; `quitSafely` добирает очередь сам.
- Страж «сервер исчез из подписки» читал `state.json` и считал пустой список
  доказательством. `StatePersistence.load()` бросать не умеет в принципе
  (испорченный файл → страховка + пустое состояние), поэтому битый или
  заблокированный файл рвал живой туннель, а redeliver отказывался
  подключаться. Теперь пустой список — «мы ничего не прочитали»: проверка
  срабатывает только когда список непуст и id в нём отсутствует.
  Проверено на устройстве в обе стороны: живой `tun0` пережил
  `this is not json at all` в `state.json` (80 с > порога в 60 с, счётчики
  шли), а исчезновение сервера из читаемого списка по-прежнему рвёт сессию.
- `stopSelf()` без startId — до сих пор мог убить уже новую сессию (пока рабочий
  поток жёл 10 с, пользователь успевает нажать другой сервер). Теперь
  `stopSelf(startId)`.
- `session` — между потоками (главный пишет, рабочий читает) → `@Volatile`;
  `endedInFailure` был защёлкой в одну сторону и переживал сессию, из-за чего
  чистый разбор не снимал последнее уведомление. Теперь сбрасывается при
  поднятом туннеле.
- `watchNetwork` перепривязывался, не снимая предыдущий callback, а
  `registerDefaultNetworkCallback` молча глотался при отказе — теперь старый
  снимается, отказ пишется в logcat.
- `Engine.startXray`/`startAwg` были единственными входами без проверки
  `available`, а `openTunnel` ловит `Exception` — `UnsatisfiedLinkError`
  (`Error`) валил процесс с уже поднятым туннелем. Проверка добавлена.
- Замеры: TLS-контекст строился **внутри** измеренного окна (на macOS — до
  `DispatchTime.now()`), DNS резолвился без потолка и давал один адрес (v6 без
  маршрута убивал все пять попыток, тогда как `NWConnection` перебирает стеки),
  `soTimeout` ограничивает один `read`, а не всё рукопожатие, `catch
  (IOException)` ронял сервер в «не мерили» без `-1` в ряду, пул круга был из
  non-daemon нитей, а поздний ответ прежнего круга дописывал ряды нового.
  Теперь: контекст до таймера, разрешение с бюджетом и порядком IPv4-first,
  жёсткий потолок попытки (`> timeout → nil`, как у Swift), `Throwable`,
  daemon-нити, отказ по поколению круга и `cancel()` при закрытии экрана.
- История: читалась и писалась на главном потоке (на macOS — detached-задача),
  `retain` сравнивал размеры ряда с чужой базой, потолок 256 был продублирован
  в двух местах. Теперь один поток `probe-io`, один константа, корректный
  сравнение.
- Экран не должен был догадываться о туннеле по «молчанию» рассылки: `fail()`
  тоже рассылает, поэтому после неудачного подключения следующий круг
  отправлялся в корзину, а после поворота экрана `lastTick` обнулялся и двойные
  отсчёты попадали в историю. Сервис теперь кладёт в сообщение
  `EXTRA_TUNNEL_UP` и id сессии, экран хранит их в объект процесса (не в
  `remember`), и правило «пишем только подключённому серверу» совпало с macOS.
- Кнопка «Замерить» больше не хранит своё представление о том, идёт ли круг
  (`probeRunning` читался сразу после запуска потока и залипал).

Чего этот проход касаться не стал, и почему: патч xray для android-сборки
(«остановить вход» и буферы — см. раздел про движок; без него каждое
переподключение оставляет живой стек) требует замера `NumGoroutine` на
переподключениях; потолок `addRoute()` для развёрнутого обхода — надо сначала
измерить, где netd говорит «нет», и выдумывать число незачем; фоновый круг
замеров раз в 3 мин, как на macOS — на телефоне это батарея, решение за
тобой; выученное маскирование в пути подключения (`LearnedMasking.profileFor`)
— на Android пока некому ничего учить, пока нет лестницы восстановления, и
подключать к нему чтение раньше, чем появится чему учиться, — преждевременно.

## Лестница восстановления (порт `attemptReconnect`)

Серия ступеней в `data/Recovery.kt`, а не в `:core`: алгоритм на macOS живёт в
`AppState`, работает с уже разобранным состоянием и золотом не сверяется —
сверять не с чем. Порядок тот же: попытка 1 — повторить того же сервера,
попытка 2 — того же, но на ступень сильнее маскированием, попытка 3+ — переход
на следующего неподобранного кандидата — по рейтинговому скору из истории
замеров (`ServerScoring.rankingScore`, тот же, что у кнопки «Лучший»), а не по
последнему пингу; потолок `maxReconnects + 5` и обратные отсечки 1→2→4→4 с.
Российский выход кандидатом не становится: блок с обеих сторон одного и того же
провайдера.

Отдельная ступенька — «нет линка» (`Step.Hold`, 5 с): без физического линка
попытка не расходуется, иначе за минуту в метро лестница выгорела бы до
`GiveUp`, а на macOS в этом месте `holdForNetwork`. Пауз — не больше `maxHolds`
(12 ≈ минута), после чего лестница всё равно делает обычную попытку:
`ConnectivityManager` отвечает «линк есть» по наличию сети без флага VPN и
ошибиться может, а `establish()` — уже настоящая проверка. Сама пауза пишется в
logcat (`hold: линка нет, пробую через 5 с`): ни широковещания, ни попытки у неё
нет, и без строки застрявший эпизод неотличим от молчания.

Замерить это можно без меня: `bash Android/Scripts/verify-ladder.sh` (обрыв) и
`bash Android/Scripts/verify-ladder.sh hold` (обрыв без линка). Скрипт рвёт
`tun0` у системы под ногами (`ip link del`, нужен `adb root`) и смотрит на logcat
и интерфейсы; если интерфейс приложения перезапустили посреди прогона, он пишет
«прогон недействителен», а не «лестница не работает» — на этом он случайно
поймал чужие `adb install` и `am force-stop`.

**Когда лестница заводится.** Только на обрыв: `StatusChannel.fail` несёт флаг
`DROPPED` (туннель до этого поднимался) — или эпизод уже идёт. Первый отказ
подключения, которое никогда не поднималось, лестницу не начинает; это ровно
поведение macOS, где `attemptReconnect` зовётся из наблюдения за упавшей
сессией, а не из отказа ручного «Подключить». Иначе опечатка в порту
заставляла бы восемь раз долбиться в нерабочий адрес и уводила бы выбор на
другой сервер.

**Что нашёл скан по пути (все три — молча работающие баги).**
- `StatusChannel.fail` не клал в интент ни `EXTRA_FAILED`, ни `EXTRA_SESSION_ID`
  (параметр `sessionId` не использовался вовсе): экран читал «это не отказ», и
  заводилась бы что угодно, но не лестница.
- В сервисе id умершего сервера читался **после** `sessionSetup = null`, то есть
  всегда `null` — лестница гадала бы о жертве по выбору на экране.
- Отказ ещё не поднимавшегося туннеля попадал в ту же ветку, что и обрыв.
- Остановка плиткой Quick Settings (`SessionActivity` → `SessionStarter.stop()`)
  лестницу не гасила: широковещание об остановке не отличалось от любого другого
  «up=false», отложенная ступенька оставалась вооружённой и поднимала туннель
  через секунду после «Отключить» (замерено на сборке 02:16: `fail:` 03:19:21.588,
  остановка принята — уведомление снято, и в 03:19:22.703 всё равно `connect`).
  Теперь у `StatusChannel.stop()` есть признак `EXTRA_STOPPED`, экран на него
  обрывает эпизод, и `SessionStarter.stop()` делает то же напрямую — приёмник
  экрана при остановке из шторки может быть вообще не зарегистрирован.
  `bash Android/Scripts/verify-ladder.sh stop` это и проверяет: на починенной
  сборке — ноль попыток и поднятый обратно туннель отсутствует 25 с.

**Проверено на устройстве** (эмулятор arm64, xray на Mac как выход, `ip link del
tun0` как обрыв): потеря интерфейса замечена за 3.7 с (два пропуска тика), попытка
через 1 с, `tun0` поднят заново (индекс 19 → 20); сценарий «сервер исчез из
подписки» прошёл Same → Escalate → Switch → GiveUp («нет рабочего сервера» на
экране); в варианте с возвратом сервера между ступенями — `connect Live 10443 with
masking maximum` в logcat и `learnedMasking = {"vless|10.0.2.2|10443|b831…":
"maximum"}` в `state.json`, после чего ручное подключение реально поехало с
maximum. Ручное «Отключить» в паузе между ступеньками не оставило ни одной
последующей попытки (24 с тишины). Отказ ручного подключения на мёртвом имени —
ни одной строки «восстановление».

Цепочка паузы без линка целиком (тот же риг, `verify-ladder.sh hold`):

```
02:24:15.402 W/Anemia: fail: Система сняла туннель (dropped=true, session=1111…)
02:24:15.422 I/Anemia: hold: линка нет, пробую через 5 с      ← UI-процесс, +20 мс
02:24:21.472 I/Anemia: connect Live 10443 with masking maximum ← попытка уже после линка
```

За время без линка — ни одной попытки; `tun0` поднялся через 3 с после возврата
сети; интерфейс жил весь прогон.

**Ограничения, названные вслух.** Лестница живёт в UI-процессе: если интерфейс
схлопнули, лечить некому (на macOS и iOS — ровно так же: координатор живёт в
приложении). Эпизод переживает поворот экрана, потому что состояние лежит в
`RecoveryEpisode`, а не в `remember` композиции, но не уничтожение Activity — на
этом прогоне как раз споткнулся чужой `am force-stop`.
Выученный профиль пишется после двух тиков (~6 с) вместо macOSовских трёх
проверок здоровья за 30 с: проверки здоровья на Android ещё нет (ждёт решения
по `probe.go`), и тик — единственное доказательство жизни. Кандидатами становятся
и немереные серверы: фонового замера, который давал бы quality-скор каждому,
здесь нет (немереные идут после мереных).
Выбор кандидата именно по истории, а не по последнему пингу, замерен на риге:
три сервера, у «B fast but unlucky» последний удачный ответ 30 мс, но три
неудачи в ряду дают скор 1342, у «C steady good» ряд 118—122 мс и скор 122.
Старая сборка на тех же данных переключилась на B (пинов в этом раунде не было
вовсе → ничья → порядок списка), новая — на C: `connect C steady good`.

Пятнадцать тестов в `app/src/test/.../RecoveryTest.kt` держат порядок ступеней,
задержки, потолок, фильтр RU, «уже пробованный», паузу без линка и её лимит;
против них убиты десять мутантов (backoff на единицу, потолок 8→9, снятие
фильтра RU, незапоминание `tried`, несброшенная эскалация, возврат на мёртвый
сервер, пауза, съедающая попытку, `HOLD_MS`, лишний `maxHolds` и несброшенный
счётчик пауз).

## Проход: статистика трафика, перенос с QR, плитка и обход по приложениям

Три золотых модуля `:core` (`Traffic`, `SyncBundle`, `Leaks`) существовали как
проверенное байт-в-байт ядро **без единого вызова из приложения** — тот же
класс проблемы, что был с мёртвым `Persistence.kt`. Здесь у них появились
вызывающие (кроме `Leaks` — его делает параллельный проход).

**Трафик.** `:vpn` при каждом тике отдаёт счётчики в `TrafficLedger`, ряд
пишется в `traffic.json` не чаще раза в 30 с — ровно как `take(_:)` на iOS.
`runStartedAt` берётся один раз за запуск движка (`сейчас − uptime` первого
тика): пересчитывать его на каждом тике — значит получать новое «имя» сессии и
записывать накопленный итог вместо разницы. Разбор сессии зовёт `stopped()` из
`closeTunnel()`, то есть со всех путей разом. Ряд удалённых серверов чистит сам
сервис (тот же `forgetServers`, что на iOS), потому что второго писателя файла
интерфейсу не положено — и «Сбросить статистику» тоже команда сервису
(`EXTRA_RESET_TRAFFIC`), а не запись из UI. Замерено: `traffic.json` с телефона
(↓257 531 · ↑119 257 · 656,4 с) перечитан `LoaderTool ledger-read` без
расхождений — сдвиг reference date в `lastRun` и `lastUsed` виден именно там.

**Перенос и QR.** `SyncBundle` из состояния + `adBlock`, файл `.anemia` через SAF
и через FileProvider, ссылка `anemia://sync/…` в буфер, QR на экране, приём — из
интента, из выбранного файла и из вставленного текста. Проверено на устройстве
полным кругом: файл `Anemia.anemia` (1214 байта) прочитан Swift'ом; ссылка,
**декодированная со скриншота экрана**, прочитана Swift'ом (`sync-read` →
`bundle version=1 … servers=vless|nope.invalid|443|…`);Mac-ссылка, присланная
интентом, показала карточку «Откуда: MacBook-Pro-from-test · Новых серверов: 1 ·
уже есть: 0», а нажатие «Добавить» добавило сервер в `state.json` (3 записи,
файл по-прежнему читается `state-read`). Повтор той же ссылки — «уже есть: 1»,
кнопка неактивна.

**Плитка и обход по приложениям.** Плитка не поднимает сервис сама — она
запускает прозрачную `SessionActivity`: с Android 12 foreground-сервис можно
стартовать только когда приложение на виду, а диалог согласия вообще не
показывается без активности. Обход по приложениям доезжает до `Builder` через
`ConfigApplier.apply`, который читает список на месте.

Четыре вещи, которые дало только измерение:

* **`SharedPreferences` между процессами не обновляются.** Первый вариант
  `AppBypass` хранил список в прайс-настройках — и живой `:vpn`, поднятый до
  правки списка, при переподключении взял бы прежний список: кэш процесса не
  сбрасывается чужой записью. Проверено на том же PID (12253): подключение со
  пустым списком, правка файла, отключение, подключение тем же процессом —
  `ip rule` показывает новую дырку. Хранилище — файл `app-bypass.txt`,
  читаемый заново на каждом `establish()`.
* **`zxing`-ный `Encoder.encode` игнорирует подсказку `MARGIN`** (замерено на
  3.5.3: матрица приходит ровно с модулями, без полей), поэтому тихая зона
  дорисовывается руками, а тест проверяет *ширину* поля, а не «где-то бело».
* **Белый квадрат вместо кода.** `Bitmap.setPixels` вызывался с `stride = 0` и
  перепутанными осями — тест матрицы этого увидеть не мог (он проверял код), и
  только скриншот с устройства показал пустое место. Раскладка пикселей
  вынесена в чистую `Qr.pixels` и закреплена тестом, но сам вызов `setPixels`
  на JVM не проверяем ничем — он подстрахован скриншотом.
* **Формы `startActivityAndCollapse` переставлены местами:** версия с `Intent`
  живёт с API 29 и устарела с 34, а версия с `PendingIntent` — наоборот,
  появилась в 34. Линт на это и наткнулся; на 28 fallback — обычный
  `PendingIntent.send()`.

Что здесь осталось незакрытым, названным вслух:

* **Камерой QR не читается.** На iOS для этого есть `QRScanner` (AVFoundation),
  здесь — CameraX + декодер; на эмуляторе камера даёт синтетическую сцену,
  поэтому проверка всё равно была бы на честном слове. приём работает со ссылкой,
  файлом и вставленным текстом.
* **Буквального нажатия на плитку нет.** Компонент виден системе
  (`cmd package query-services`), перегрузка в dex правильная (`dexdump`), и
  действие плитки (`SessionActivity` → `tun0` с адресами плана и нужными
  `uidrange`) проверено. Но добавить плитку в шторку на этом образе нечем:
  `cmd tile` отсутствует, а `settings put secure sysui_qs_tiles` не
  применяется. Это проверка на своём устройстве.
* **Кнопки «Перенос» и «Мимо VPN» нет на основном экране.** Экран в этом
  проходе был занят другим проходом, поэтому у обоих экранов свои точки входа:
  долгое нажатие на значок (App Shortcuts), файл `.anemia` и ссылка
  `anemia://sync/…`. Одна строка в навигации экрана — то, что стоит добавить,
  когда экран свободен.
* **Несуществующий пакет в списке обхода** туннель не рвёт (проверено:
  `com.example.notinstalled` + живые `tun0`), но и предупреждения в логе не
  было — Android молча игнорирует неизвестный пакет, так что ветка
  `onFailure` в `ConfigApplier` остаётся подстраховкой без оракула.

## Карта: география из того же Swift-источника

`iOS/Anemia/WorldMap.swift` + `MapData.swift` — последний крупный экран, которого
в Android не было. Он перенесён в той части, которая статична, и перенесён так,
чтобы числа не переписывались руками.

- **`Scripts/golden-map.sh`** компилирует `iOS/Anemia/MapData.swift` вместе с
  эмиттером (одним модулем) и выдаёт `app/src/main/assets/map.json` — геометрия,
  42 кольца берегов, 94 центра стран — и два золота: `map/dots.golden.txt`
  (3826 сот, которые насчитал Swift) и `map/points.golden.txt` (35 вердиктов
  «суша или море»). Приватные массивы кольца читаются через `Mirror`: править
  iOS-файл ради андроидного прогона не пришлось.
- **`core/…/MapGeo.kt`** — порт выборки: те же 68 рядов по 2°, тот же сдвиг
  нечётных рядов, то же чётно-нечётное переключение по кольцам, порядок
  арифметики сохранён буквально (`(lon + 180) / 360`, `latTop - 1 - row * 2`),
  иначе последняя операция дала бы другой последний бит.
- **`app/src/test/…/MapGeoTest.kt`** сверяет соты и вердикты побитно (тот же
  приём, что с рейтингом: Foundation и JVM печатают дроби по-разному), и
  отказывает на кривом ассете вместо пустой карты. Тест живёт в `:app`, потому
  что ассет — ресурс приложения; фикстуры при этом в `core/src/test/resources`,
  как всё остальное золото.
- **`ui/MapActivity.kt`** рисует соты Canvas'ом: тёплые страны, где лежат
  серверы (радиус 7°, как на iOS), метка выхода, подпись страны по нажатию и
  выбор лучшего сервера страны, пока туннель не поднят. Вход — ярлык долгого
  нажатия на значок; кнопки на основном экране нет (экран занят другим
  проходом).

Замер на устройстве (1080×2400, полоса карты 1075×406): **все 3826 сот** встали
в ≤1 px от расчётного положения — медиана 0, 90-й процентиль 0, максимум 1.
Открытый океан подтверждает обратное: в точках (0°, −150°) и (−30°, −20°) нет
ни одной нарисованной точки в радиусе 24 px. Узкие моря этим трейсом не
проверяются вообще: шаг сетки 2° — это ~3 px на карте во всю ширину экрана, и
«ближайшая точка в 2 px» у Красного моря означает лишь то, что соседняя сота и
должна стоять рядом. Сама же корректность точки внутри полигона закреплена
золотым файлом из 35 вердиктов, а не пикселями.

Мутации против этого золота: пять убиты (снятие чётно-нечётного переключения,
перестановка lon/lat при разборе кольца, bounding box по чужой оси, `isLand` с
`break` вместо переключения, `y` без вычитания нижней границы). Выжили две, и
обе эквивалентны по той же причине, по какой выживают `u%04x` без `Locale.ROOT`:
расширение `lat > maxLat` на 1° не может изменить ответ — при `lat` выше всех
вершин условие `(lats[i] > lat) != (lats[j] > lat)` просто никогда не
переключается; а `lon >= 180` против `lon > 180` различалось бы только если бы
кольцо имело вершину восточнее 180°, чего в таблице нет (максимум ровно 180°, и
`lon < crossLon` там ложно).

Чего из `WorldMap` на Android нет и почему: «вы здесь» и дуга маршрута берут
начало из домашней страны, а она приходит из проверки утечек (адрес провайдера),
которая сейчас дописывается в другом проходе; бегущие по дуге пакеты и 30 fps —
отдельный `TimelineView`, и без домашней точки рисовать их не от чего.

## AmneziaWG: живой движок против Kotlin-скрипта

Ветка `awg://` висела первым номером в «незакрытых рисках»: движок на Android
поднимается (переход на `CreateUnmonitoredTUNFromFD` снял `setMTU` и netlink),
но чтобы *настоящий* AmneziaWG согласился говорить с тем, что собирает Kotlin,
никто не проверял. Золотая сверка этого доказать не может: у Swift и Kotlin
может оказаться один и тот же неверный ключ.

- **`Scripts/verify-awg-kotlin.sh`** компилирует `:core` с крошечным CLI
  (`Scripts/awg-uapi-kotlin/main.kt`), берёт из него UAPI-скрипт и прогоняет его
  через настоящую `amneziawg-go` — тем же харнесом, что и
  `Scripts/verify-awg-engine.sh`, только клиентский скрипт приходит из порта.
  Замерено: `client → server: first delivery on attempt 1`,
  `server → client: attempt 1`, `steady state: 40 packets delivered without a
  retry`, и отдельно — отказ движка на base64-ключ вместо hex.
  Проверка начинается с того, что **каждый** параметр обфускации доехал до
  скрипта (`jc/jmin/jmax`, `s1…s4`, `h1…h4`, `i1`, `header_protection_key`,
  `content_padding_addition`, `rekey_after_time`, `keepalive_timeout`,
  `max_handshake_attempts`, `random_trailers`, `disable_cookies`, `endpoint`,
  `allowed_ip`): на отсутствующий ключ движок молча берёт значение по умолчанию,
  и «совпадает со Swift» это не ловит. Два мутанта (лишняя буква в имени
  `jc`, выброшенный `random_trailers`) красные.
  Поймано и по ходу: `uapiScript(server, endpointAddress)` ждёт **адрес**, порт
  он берёт из сервера — первая версия прогона передавала `host:port` и движок
  отказывался с `ParseAddr("127.0.0.1:58785"): unexpected character`.
- **`Scripts/awg-peer.sh`** поднимает сервер `amneziawg-go` на настоящем UDP-порту
  и ждёт рукопожатия с устройства (`Scripts/awg-harness/awg_live_peer_test.go`,
  тот же пакет `device`): печатает статус раз в 2 с и выходит нулём, когда
  `last_handshake_time_sec` перестал нулём и `rx_bytes` двинулся. Пир
  стартует, ждёт и корректно репортит отсутствие клиента — но **прогона с
  эмулятора пока нет**: к моменту, когда он понадобился, устройство и
  установленный APK были заняты вторым проходом (пересобранный `libanemia.so`,
  правки в `MainActivity`/`LeakScreen`), и втыкаться в чужой прогон я не стал.
  Это остаётся единственной незакрытой частью ветки: что дескриптор от
  `establish()` доходит до AWG-движка и интерфейсы поднимаются — проверяется
  только на устройстве.

## Проход: отказ здоровья уходит на другой сервер, круги проверки утечек, честный замер скорости

Скан в четыре независимых прохода (сервис, слой данных, интерфейс, эталоны +
шим), дальше каждая находка перечитана в коде: три оказались неверны, десять
исправлены. Сборка после всех правок: `assembleDebug` + `lintDebug` (0 ошибок) +
29 unit-тестов, `test-core.sh` — 41 проверка в трёх локалях.

**Переключение по здоровью до этого не переключало ничего.** Вердикт `Go` звал
лестницу восстановления, а лестница с `attempts = 1` отвечает `Same` —
переподключение к тому же выходу, который дважды подряд не пропустил запрос.
Эпизод гас на втором тике «поднят» (6 с, здоровье меряется раз в 30 с), слот
бюджета был потрачен: три таких холостых цикла глушили автопереключение на
четверть часа. Теперь у эпизода есть причина — `Recovery.begin(losing,
viaHealth = true)` делает первой ступенькой `Switch` (после ухода `viaHealth`
снимается, и дальше лестница ведёт себя как при обрыве), ровно как iOS, где
`.go` — это `switchToFastest`, а не `attemptReconnect`. Три теста в
`RecoveryTest`. Замерено на эмуляторе с локальным выходом: сервер заглушён →
`health: … (подряд 1)`, `(подряд 2)` → через секунду `connect C steady good`.

**Отметка «за туннелем следят» теперь стоит той же опции, что и на iOS**
(`tunnel.wantsHealth = { autoSwitch }`). Без гейта `:vpn` ходил в `gstatic`каждые
30 с настоящим DNS+TCP+TLS через выход, когда вердикт не читал никто. Измерено в
access-логе того же выхода: с включённой опцией — ровно одна строка `accepted
tcp:www.gstatic.com:443` на такт, с выключенной — ни одной за полтора минут, при
том что `tun0` остаётся `UP,LOWER_UP`.

**AmneziaWG: показание засчитывается только настоящее.** `Engine.status` отдаёт
не-null почти всегда (`AnemiaStatus` отвечает всеми восемью ключами, а
сорвавшийся `IpcGet` — это тройка нулей), и нулевая базовая линия стоила дорого:
следующая дельта равнялась уже накопленным байтам, `received > 0` читалось как
«проверка пройдена», полоса отказов не доходила до порога — автопереключение для
`awg://` не наступало бы никогда. Страж скопирован с iOS-`checkHealth`
(`engine == "awg"` и оба счётчика на месте), заодно он больше не штампует
`healthCheckedAt` по нулям, то есть `signalFresh` не врал про свежее показание.

**`LeakChecker` умел только начинать, но не отменять.** `run()` при возврате на
экран обнулял общий флаг отмены — и разоружал ещё живой прошлый круг: тот
дочитывал ходы сквозь туннель (чужой, уже не нужный платный трафик) и поздним
отказом помечал «измерить нечем» уже новый отчёт через общий
`tunnelUnmeasured`. `isRunning` читался из подписи, которую `cancel()` гасил
сразу, поэтому кнопка оживала при живых потоках. Состояние стало принадлежать
кругу (`Round(id)` со своим списком потоков, `alive()` вместо флага, `join` с
потолком, освобождение флага в `finally`), появилась вторая фаза «Проверяю DNS…»,
а `exitUnmeasurable` ставится только когда движок не ответил вовсе или система
отказала в привязке сокета — мусорный ответ сервиса больше не выдаётся за
диагноз про сеть туннеля. Проверено на устройстве: два полных прогона в одном
процессе, `leak: LEAKS выход=… dns=18 не_измеримо=false`, зависшего флага нет.

**Замер скорости больше не рисует скорость там, где сервер отказал.** Код ответа
читался после тела, а `inputStream` на 4xx/5xx бросает — то есть проверка статуса
была недостижима, и 25 МБ отклонённой загрузки оставались в счётчике: отказ
попадал в «Прошлые замеры» как настоящее число. Теперь статус читается до тела,
непринятые байты списываются, латентность меряется с 8 с (как `timeoutInterval` у
Swift) вместо 30, у цикла наблюдения есть `finally`, потоки пула — демонические, а
«Остановить» больше не подписывается «Готово» по оборванному кругу. Замечено и
сказано вслух: macOS/iOS в том же месте байты отказавшего запроса оставляет
(`SpeedTester.Meter` считает отправленное до кода ответа) — Android теперь строже.

**Фоновое переподключение не убивает интерфейс.** Ступенька лестницы догоняет
экран при погашенном телефоне, а с Android 12 foreground-сервис из фона не
поднимается: без обёртки `ForegroundServiceStartNotAllowedException` прилетал в
скоуп без обработчика, то есть гибель интерфейса вместе с эпизодом. Теперь отказ
перехвачен, эпизод закрыт, а человеку сказано, что нужен открытый экран.

**Шим больше не выдаёт отказ за успех.** `take()` возвращал NULL и когда строка
ошибки не передалась через JNI (Modified UTF-8 не возит 4-байтные
последовательности, а имена серверов — флаги-эмодзи, которые Go возвращает в
цепочках), то есть Kotlin читал это как «движок принял конфиг»: мёртвый движок с
«подключено» сверху. Теперь неотмаришаленная ошибка доезжает текстом, `-4`
отделён от `-3` (нет символа / не передался аргумент), а `AnemiaFetch` при
неотданном URL отвечает JSON-ошибкой вместо NULL.

Мелочи, каждая — из того же скана: `tick`/`healthTick` обёрнуты (необработанное
исключение из сообщения `Handler` — это гибель `:vpn` с живым туннелем, без
записанного трафика и без причины), `endedInFailure` стал `@Volatile`,
перепривязка сети зарегистрирована на рабочем потоке (иначе
`AmneziaNetworkChanged` стоит в главный поток процесса, а это ровно то ANR-окно,
от которого весь сервис уже уведён на `worker`), ветка `FETCH` освобождает свой
`startId` когда туннеля нет, `AnemiaFetch` больше не хвастается «тем же
мьютексом, что и stop» (Go берёт `mu` только чтобы списать указатель — комментарий
говорит правду: тот же гонка с закрывающимся экземпляром, и та же цена —
«Отключить» подождёт уходящий ход). `ProbeHistory` не превращает мусор в «0 мс»,
`QrTest` перестал быть «иногда красным» (случайные id серверов на потолке QR
версии 40), поля ввода переживают поворот, `MapActivity` узнаёт живой туннель у
системы и читает свежие списки в жесте, `StatsScreen`/`AppsActivity`/
`TransferActivity` больше не читают диск, не врут про «не установлены» и не
пересобирают QR на каждый символ, чужой файл принимается с потолком, а не
`readBytes()`, а из процессных синглетонов убраны Activity. В `verify-ladder.sh`
режим `stop` снова снимает лог перед вторым подсчётом — иначе `later == stopped`
буквально и «туннель воскрес» поймать нельзя.

Что осталось и почему: `stopSelf(lastStartId)` после незапланированного разбора
(отметка «самый свежий startId» сдвигается каждой отметкой экрана, а наивный
перенос присваивания убивал бы новую сессию; следствие мягкое — процесс висит, но
`tunnelUp` требует ещё и `tunN`, поэтому интерфейс не врёт); `onBind` = null и
always-on VPN (решение по продукту плюс проверка на устройстве); `HEALTH_TIMEOUT_MS`
4 с против iOS 8 с и `latency = 1` у AWG (в `:vpn` нет пингера) — задокументированные
выборы; запись выученного маскирования после двух тиков без доказанного здоровья;
`-1/-2` в шейме по-прежнему сливаются с `-3` на стороне Go; AWG-ветка не проверена
живым сервером. Эталон подписки (`sub/headers.golden.txt`) обновлён другим проходом
после его клампа `usedFraction` — к правкам этого отношения не имеет.

**Выученное маскирование теперь ждёт доказательства, а не двух тиков.** Ветка
«туннель поднят внутри эпизода» закрывала эпизод и записывала профиль после
`STABLE_TICKS = 2` — это 6 с, тогда как первая проверка новой сессии приходит не
раньше 30 с (плюс пауза «за нами следят»). То есть профиль запоминался бы по
поднятому, но ещё не пропустившему ничего туннелю. Теперь запись ждёт свежее
показание здоровья (`EXTRA_HEALTH_FAILURES` пришло числом), а молчащий движок —
`HEALTH_GRACE_MS = 60 с`, после которых тики снова считаются доказательством:
старая `libanemia.so` или AWG без счётчиков не должны оставлять эпизод навсегда.
Заодно `LeakSection` читает отчёт, фазу и признак «идёт» одним снимком
(`LeakSnapshot`), а не тремя `remember` в три разных момента.

Тот же экран, следующий проход: строки «IPv6» и «DNS» ставили галочку по одному
только факту, что туннельная проба ответила. На iOS им мало этого — нужны ещё
адрес «до VPN» и не совпавшая страна (`sameCountryAsHome`), потому что ядро при
совпавшей стране сравнивать резолверы и IPv6 отказывается (`LeakCheck.findings`
возвращается раньше). Значит «Через VPN: <адрес>» рисовался там, где сказать нечего,
на экране, чья работа — не утешать. Теперь оба случая подписаны причиной и
помечены «не проверено», правило страны переехало в отчёт и закреплено тестами.

Три прогона `verify-ladder.sh` на финальной сборке (обрыв, пауза без линка,
остановка в паузе): `drop` — «✓ tun0 поднят сам через 4 с», первая ступенька
по-прежнему `Same` (ветка здоровья её не сдвигает); `hold` — «✓ без линка попыток
не было, после возврата сети лестница пошла с первой ступеньки», 3 паузы и ноль
списанных попыток; `stop` — «✓ остановка в паузе погасила эпизод: 0 попыток, tun0
не поднят». Что новый подсчёт в `stop` не мертвец, доказано отдельно: свежий
`logsnap` после тапа поднял счётчик с 0 на 1, когда в буфер попала новая строка
`connect` (в старом коде оба числа читались из одного и того же снимка).
`verify-tunnel.sh` на той же сборке: 14 маршрутов, 2 default, 11 правил
`lookup tun`, счётчики движка идут (104 → 111 КБ), UID приложения вне туннеля.

**Отмена освобождает экран сразу.** Первая версия правки держала «круг идёт» до
тех пор, пока потоки отменённого круга не досмотрят ходы — то есть ушедший и
вернувшийся экран не мог запустить проверку секунд двадцать. Отдельного флага
теперь нет: занятость = «есть круг», а `cancel()` снимает круг с дежурства сразу
(после отметки поколения он уже ничего не опубликует и не напишет — всё его
состояние принадлежит ему), а `finish()` освобождает слот только если это всё ещё
его круг. Цена названа вслух: ход, уже ушедший в движок, отменить нельзя —
`:vpn` досматривает его до `timeoutMs`, и эти секунды трафика через выход после
ухода с экрана остаются. На устройстве проверено: круг, снятый на середине, не
опубликовал ничего, а следующий стартует через секунды и публикует ровно один
вердикт (`leak: LEAKS выход=… dns=16 не_измеримо=false`).

**Живой AWG-пир нашёл то, чего эталоны не видят в принципе.** Ветка `awg://` на
устройстве умирала на старте движка: `awg config: IPC error -22: invalid UAPI
device key: set`. Причина — в том, как скрипт скармливается: `device.IpcSet` —
это тело операции `set`, а рамочную строку `set=1` читает сокетный `IpcHandle` и
только потом зовёт `IpcSetOperation`; парсер же видит строку `set=1` как ключ
`set` и отказывает. Наш эмиттер пишет рамку намеренно (с ней скрипт читают
`Scripts/awg-harness` и золотые сверки — `verify-awg-kotlin.sh` прогонял его
через сокетный путь и потому всегда был зелёным), так что снимается рамка, а не
меняется формат: `uapiBody` в `iOS/Engine/engine.go`, четыре Go-теста на неё
(включая «\\r в рамке» и «скрипт без рамки не сдвигаем»), мутант «ничего не
срезать» краснит три из четырёх. Правка в общем движке — значит и `.ipa` до
пересборки `iOS/Scripts/build-engine.sh` не умел `awg://`.

**Правило приёма показания вынесено в предикат и проверено мутантами.** Три
условия, которые к утру жили строчками внутри `checkHealth`, переехали в
`vpn/AwgReading` — по той же причине, что и `TunnelHealth` с `HealthSchedule`:
правило, которое видно только на устройстве, нельзя закрепить устройством.
Семь тестов, четыре мутанта («нули пропускаем», «отмотку не видим», «чужой
движок пропускаем», «ключи наоборот») — все убиты. На устройстве после переезда
тот же прогон с живым пире: `PEER VERIFIED … 268 bytes`, `tun0 10.66.0.2/32`,
ни одного «не засчитано» за здоровое окно, после смерти пира два отказа и
`connect C steady good`.

**Девятый проход — харнесс, который перестал врать, и чтение файла вне главной
нити.** `verify-doze.sh` в первой версии моей же правки стал проверкой тривиально
истинного: он вносил приложение в белый список doze и потом рапортовал, что часы
шли. Теперь наоборот — процесс ИЗ белого списка выносится (и состояние списка
ловится до и возвращается после: скрипт меняет системную политику), режим
`mState=IDLE` допрашивается опросом с десятисекундным ожиданием, потому что
`force-idle` DeviceIdleService применяет в своём обработчике. Прогон: 215 с →
240 с за 25 с простоя при погашенном экране, `tun0` цел, выход 0. В
`verify-ladder.sh` снят интерфейс больше не считается гибелью прогона (на части
прошивок система убирает его вместе с подложкой — красным становится только
«интерфейс жив и до приложения не дошло»), а честное сравнение `count_agents` с
`hasPhysicalLink` названо прокси: настоящим доказательством паузы объявлена
строчка `hold:` в логе самого приложения. Режим `hold` перепрогнан: три паузы,
ноль списанных попыток, `tun0` вернулся сам через 6 с. В `TransferActivity`
чтение принесённого файла переехало в `Dispatchers.IO` с заглушкой
«читаю принятые данные…», а «не похоже на перенос» наконец говорится словами.

**Шестой проход: свежий взгляд на собственные правки того же дня + углы, которые
никто не сканировал.** Два независимых сканера (диф сегодняшних изменений и
`ConfigApplier`/`StatusChannel`/`TunnelFetch`/плитка/манифест), и первая же
находка оказалась дырой в моём же страже AWG:

- **Нулевое показание AmneziaWG проходило проверку наличия ключей.**
  `awgTraffic` на сорвавшемся `IpcGet` возвращает `(0, 0, 0)`, не теряя ни
  одного ключа и `engine = "awg"` (`engine.go:337-340`), — то есть страж
  «движок назвал себя и понёс счётчики» пропускал ровно тот случай, ради
  которого и был написан: нуль садился базовой линией, следующая дельта равнялась
  накопленным байтам, `received > 0` читалось как «пройдено». Теперь показание
  принимается живое: хоть один счётчик ненулевой, и ни один не отмотался назад
  (за время жизни движка накопленные байты только растут). **Та же дыра осталась в
  `iOS/AnemiaTunnel/PacketTunnelProvider.swift:305-306`** — правка написана здесь,
  а не в чужом файле, потому что его в этот же вечер правил другой проход.
- **`LeakChecker` мог занять слот навсегда.** Я же и сломал: `measure` ловил
  `Exception`, а `hops` поднимает до девяти нитей — на пределе нитей JVM бросает
  `OutOfMemoryError`, который шёл мимо освобождения, и синглтон на весь процесс
  оставался «идёт проверка» без единой живой проверки. Теперь `Throwable`, плюс
  `finish()` вызывается, если нить вообще не поднялась.
- **Два «параллельных» хода сквозь движок были ложной параллельностью.**
  `:vpn` обслуживает fetch'и на одном рабочем потоке (и свести его в очередь
  нельзя — `AnemiaFetch` держит экземпляр, который `stopLocked()` закрывает), а
  терпение просителя (`timeoutMs + REPLY_GRACE_MS` в `TunnelFetch`) очередь не
  покрывает: второй ход возвращался пустым, и **здоровый выход показывался как
  «не измерено»**. Через движок ходы теперь идут последовательно (голым сокетом —
  по-прежнему параллельно), то же касается шести резолвингов bash.ws: им нужно
  дойти до резолвера *до* того, как спросится отчёт, а `join(14 с)` был короче
  одного хода (15 с). Ответы пишутся в `AtomicReference`, а не в ячейку массива:
  немой чтение после таймаута `join` не обязано увидеть записанное. DNS-фаза
  ограничена 60 с, чтобы медленный выход не держал экран вечность.
- `SpeedTest`: после списания байтов отказавшего потока разница двух наблюдений
  могла уйти в минус — и курс, и итог теперь не ниже нуля.
- Выученное маскирование требует подтверждения, а не часов: `healthFailures == 0`
  (свежая проверка сказала «прошло»). Проверка `young` по `EXTRA_SESSION_START`
  одна не годилась — `signalFresh` гаснет, стоит экрану уйти в фон, и профиль
  учился бы по таймеру. Без доказательства эпизод всё равно закрывается (иначе
  висел бы), но ничего не записывает и говорит почему в лог.
- `MapActivity`: `TunnelLive.up || systemUp` умел только включать запрет.
  Молча убитый сервис оставлял первое поле `true` навсегда — теперь только
  системный источник.
- `ConfigApplier.endpointOf` резолвил эндпоинт одной попыткой на 4 с, а iOS даёт
  четыре окна по 2 с: резолвер, ответивший со второй попытки, на Android значил
  «сервера нет». Заодно убран комментарий про «резолв стоит в `onStartCommand` и
  уходит в ANR» — `plan()` вызывают из `openTunnel` на рабочем потоке, и ничто
  не мешало держать контракт.
- Плитка читала `state.json` на главной нити при каждом открытии шторки — чтение
  ушло на свой поток, состояние и label остаются мгновенными.
- Удалён мёртвый `parseTunnelAnswer` — ответ движка уже разобран в `Engine.fetch`,
  и в файле не осталось ни одного вызова.

**Проверено и признано верным** (чтобы следующий сканер не тратил на это время):
счёт startId в сервисе — осознанный обмен (команда с самым свежим id срывает
сессию, а разбор по id сессии оставляет процесс висеть; `tunnelUp` требует ещё и
`tunN`, поэтому интерфейс не врёт); перепосты `tick`/`healthTick` не сдваиваются;
`viaHealth` не выживает ни `Hold`, ни `GiveUp`; порядок `notice → revision → busy`
внутри одного `view.post`; `rememberSaveable(incoming)`; `uapiBody`; разборы
split-tunnel/DNS/MTU/семейств адресов против `TunnelPlan.swift`; манифест
(экспортируемые компоненты, FileProvider, `foregroundServiceType`) и R8-keep для
JNI.

Ужесточённое правило показания AWG проверено на том же живом пире отдельно:
сессия поднялась (`PEER VERIFIED: handshake settled, 308 bytes received`), ни
одного «показание не засчитано» за здоровое окно, а после смерти пира —
`health: … (подряд 1)`, `(подряд 2)` и через две секунды `connect C steady good`.
То есть правило не отменило тот самый путь, ради которого оно написано: keepalive
крутит `tx`, `rx` стоит — отказ считается.

Замер на устройстве после всех шести правок: `tun0` поднят, проверка утечек идёт
последовательно и честно (14:43:43 → 14:43:53, все шесть резолвингов дошли до
резолвера, `leak: LEAKS … dns=18 не_измеримо=false`); `test-core.sh` — 43 проверки
в трёх локалях; `assembleDebug` + `lintDebug` (0 ошибок) + 29 unit-тестов.

## Как проверить, что сборка не врёт

```bash
bash Android/Scripts/test-core.sh           # компилирует :core и гоняет его проверки (число закреплено в самом скрипте)
bash Android/Scripts/build-engine.sh        # → libanemia.so + шим на каждое ABI
cd Android && ./gradlew :app:assembleDebug  # → app/build/outputs/apk/debug/app-debug.apk
cd Android && ./gradlew :app:lintDebug      # 0 ошибок
bash Android/Scripts/verify-tunnel.sh 'vless://…'   # туннель на подключённом устройстве
bash Android/Scripts/verify-ladder.sh [drop|hold|stop]  # обрыв, пауза без линка, остановка плиткой
bash Android/Scripts/verify-doze.sh 40            # туннель и наблюдатель под doze
bash Android/Scripts/verify-awg-kotlin.sh  # UAPI из Kotlin сквозь настоящую amneziawg-go
bash Android/Scripts/awg-peer.sh            # живой AWG-пир на UDP-порту, ждёт рукопожатия с устройства
bash Android/Scripts/golden-map.sh          # карта: ассет и золото сот из iOS/Anemia/MapData.swift
python3 Android/Scripts/subscription-panel.py       # локальная панель подписок (127.0.0.1:8080)
```

Пять команд сборки прошли на этой машине (2026-09-26): APK — 156 МиБ на три
ABI, туннель поднимался на эмуляторе Android 16/arm64 и пропускал через себя
трафик других приложений. Шестая — не «проходит», а поднимает локальный сервер,
пока крутится. `bootstrap.sh` при этом всё ещё говорит про CMake — он не нужен,
шим собирается прямым вызовом clang.

Чтобы повторить прогон целиком: `bash Android/Scripts/build-engine.sh`
(движок на три ABI — 100 МБ нативного кода в APK), затем `adb install -r`,
затем `adb shell am start -n app.anemia/.ui.MainActivity --es link '<ссылка>'`
и два нажатия: «Подключить» и «OK» в системном диалоге согласия.
